# WO-145 - native dependency census (Modding Tools build -> retail)

Companion to `docs/WO-145-retail-census.md`; the same rows as `docs/WO-145-native-dependencies.csv` (the CSV carries the full anchor text, the probe
specification and the notes; this page truncates long cells). **Read-only work order: nothing here was run against a live game.**
Paths are placeholders: `<MT>` = the Modding Tools install (app 2429020, game 1.5.5, about 40 module DLLs), `<RETAIL>` = the retail install
(app 1771300, game 1.5.6, one `WHGame.dll` monolith plus a thin exe).

## What a row is

One row per place where the native DLL (`native/KCDMP/*`, 29,277 lines read in full by four census readers plus the threads/injector reader) finds or assumes a
piece of the engine: a named export, a string literal, an RTTI class, a vtable slot, a hard-coded module+RVA, a byte pattern, a field offset inside an
engine object, or an engine global. Facts that recur in several files are one row (the `WO` and `source` cells list every user).
OS, STL and our own code are not rows. 579 rows came out of 599 raw rows after merging duplicates.

| column | meaning |
|---|---|
| id | `D-nnn`, numbered by the first work order that needed it, then by source file and line; stable within this census |
| WO | work order(s) that added it (`pre-WO-4` = the first native bring-up, before the numbering) |
| module | the Modding Tools module DLL that holds the anchor (`multi` = scanned across modules, `data/other` = not a binary anchor) |
| kind | export, string-anchor, rtti, vtable-slot, fixed-offset, prologue-bytes, struct-field, global (plus `data` for game-data and working-directory names) |
| anchor | the string, decorated class name, export, slot, bytes or offset as the code has it (truncated here) |
| hook | how the DLL intercepts it, if at all: none, inline-gate, detour, vtable-swap, iat |
| thread | where our code touching it runs: `main` (our frame hook's thread), `worker` (our plugin thread), `pipe` (our pipe thread), `engine-any` (inside a hook callback that can fire on whatever thread the engine calls from) |
| retail class | A / B / C / D, defined next |

## Retail classes (assigned by static checks against the retail `WHGame.dll`, 1.5.6; rules in section 3 of the census)

* **A** - found as-is: the same anchor works unchanged (the same string is referenced by exactly one function; the RTTI class and vftable exist; the same vtable slot passes the same byte checks; the same byte pattern matches once).
* **B** - a new anchor is clear: the class, string, registration name or function is reachable in retail, but the literal differs, is ambiguous, or the slot/offset/layout must be re-derived and re-checked.
* **C** - needs real reverse engineering: no anchor in the row reaches anything in retail (absent literal, absent class RTTI, absent export with no route, a raw RVA, a pattern that matches nothing).
* **D** - not a binary anchor: a name that lives in game data (Scripts/Tables paks, identical in both builds) or a working-directory file of ours.

A is a *static presence* verdict. It never proves the same meaning, only that the same anchor still finds one thing; B and C rows carry the real cost.

## Modding Tools-only assumptions, in one place

* 92 `export` rows (and the RTTR ABI behind most of them) resolve mangled C++ symbols by name from split module DLLs. Retail `WHGame.dll` exports 42 names, only two of them C++ (`CreateGameStartup` and `C_Game::CreateInstance`), the rest vendor SDK exports. **(data-verified)**
* 17 split-module names (plus `WHGame.dll`) are looked up with `GetModuleHandle("<name>.dll")`; on retail only `WHGame.dll` (and the exe and the third-party DLLs) are modules. The plugin's first gate waits for `CrySystem.dll` and exits. **(code-verified; retail module list inferred from the file set and import table)**
* The frame hook is an import-table swap on `WHGame.dll`'s import of `Framework.dll`; retail `WHGame.dll` imports neither `framework.dll` nor `crysystem.dll`. **(data-verified)**
* 5,630 `__FUNCTION__`-style `wh::ns::Class::Function` strings exist across the Modding Tools modules; retail keeps almost none. Of our 18 anchors of that kind, 16 are absent from retail and 2 would need widening. The `wh::ns::Name` strings that *do* survive are RTTR registration and type names (for example `wh::rpgmodule::StopFight`, `wh::rpgmodule::Soul.Guid`). **(data-verified)**
* The console commands `wh_ai_PauseNPC`, `wh_ai_ResumeNPC`, `wh_ai_NPCStateResetElement`, `wh_sys_LoadGame`, `wh_concept_HasteTrigger` and the two fall-damage cvars are literals present in the Modding Tools modules and absent from retail. **(data-verified, see census section 5)**
* Fixed `module+0xRVA` values, struct offsets and vtable slot numbers were all derived on the 1.5.5 Modding Tools modules; the one offset checked on both builds differs (`C_Actor` combat-actor field: +0x300 here, +0x278 retail, WO-67). **(code-verified and data-verified)**
* Per-area detail lives in the four `mt_only` lists of the census readers; the decisive ones are summarised in the census, section 1.
